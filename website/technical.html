How CaptainsLog works

A recording becomes a Markdown note through a shared local pipeline. Follow the modules, saved checkpoints and runtime behavior below.

One core, two frontends

The Mac app and CLI share CaptainsLogCore for recording, processing, configuration and search. The app adds SwiftUI presentation and activity coordination; the CLI invokes core operations directly.

Configuration is persisted outside UI lifecycle state. The pipeline loads settings for a processing run; personal context and spelling corrections live in separate files under the data directory's context/ folder. See ADR-017 and ADR-027 for the configuration and shared-processing decisions.

From recording to note

The default pipeline saves each stage separately. Whisper produces the transcript; Qwen handles cleanup and the remaining text stages. One Qwen model container is loaded after transcription and reused across those stages within a processing run.

These arrows show execution order. Categorization, naming and enrichment each consume the cleaned text; they do not repeatedly rewrite the previous stage's output. Category and filename results determine where the final note is saved.

stem identifies the recording and its early artifacts. slug is the generated note filename without .md; the slug marker connects it to the original stem. For example, a synthetic recording 2026-11-08-1000.m4a might keep that stem through cleanup and produce logs/personal/2026-11-08-shuttle-check.md.

Pipeline.detectNextStage checks prerequisites in table order and resumes at the first incomplete stage, reusing preceding saved outputs. A completed note alone does not make an entry complete when earlier prerequisites are missing. Reprocess removes that recording's derived artifacts and starts again from preserved audio. See ADR-016 for stage isolation. Early transcription during recording and the opt-in combined-metadata experiment are additional paths; the diagram describes default stage processing.

Processing ownership and pause/resume

ProcessingCoordinator owns one serial app worker. AppLifecycle owns its state and queue, alongside concurrent recording, model-setup and update activity. Recording is therefore independent of whether the processing worker is running. The CLI uses the same core pipeline without the app's UI queue.

A recording completes → AppState queues its stem → model readiness prepares the request → the worker detects saved progress → Pipeline.resume processes it → the app refreshes entries. Resume, Process pending, Reprocess and completed recordings all submit to this worker. Requests can wait while models download or while a previous worker drains.

Pause cancels the active task and clears waiting requests. Native work may still be returning, so ownership of the active recording persists until the worker finishes. New requests wait for that handoff; normal resume detects the next stage when the request starts. Reprocess deletes outputs during preparation, so pausing a waiting reprocess request keeps those outputs deleted.

The app worker queue and native inference gate have different jobs: NativeInferenceLifecycle serializes native operations and drains native resources during shutdown. Quit also waits for recording finalization; the AppTerminationCoordinator races graceful teardown against a two-second deadline, requiring audio closure before the deadline exit.

For changes to app processing or queue behavior, run make tests; make tests-unit excludes coordinator coverage. Model-backed fixture evaluations separately check stage output quality; neither a diagram nor deterministic tests establish native inference quality. See Testing.

Canonical notes and derived search

Completed Markdown notes are canonical. The SQLite search index is disposable and can be rebuilt from them; it does not replace the notes.

Synchronization scans completed entries, fingerprints their contents, chunks text and obtains E5 embeddings. It reconciles changed/deleted entries and rebuilds when schema, model identity or chunking metadata changes. Queries synchronize by default, then retrieve keyword matches with FTS5/BM25 and fill remaining slots using semantic matches. App query debounce and cancellation belong to SearchManager; ranking and index behavior are shared with the CLI. Search retrieves notes without generating Qwen answers. See ADR-019 for the decision.

These are the default model selections. Whisper and Qwen settings can select configured models; the E5 model is pinned for search-index compatibility. The text pipeline reuses one loaded Qwen container across its stages within a processing run.

Initial setup downloads the processing models; semantic search downloads E5 on first use. Once downloaded, inference runs on the Mac without uploading recordings or notes. See the source defaults in Transcriber.swift, LLM.swift and Embeddings.swift.
