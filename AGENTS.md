# Repository Instructions

Read `README.md` before working here. Follow its product requirements, build instructions, and design decisions.

## Backlog

- Keep one task per coherent outcome. Put research, implementation and verification phases inside it; split only independently useful outcomes. When consolidating, preserve scope and findings, redirect dependencies and archive superseded tasks without marking their implementation complete.
- ALL task content must come from the owner. Agents may edit, rewrite, clarify or organize owner-provided wording, but must never originate task content, including descriptions, scope, requirements, acceptance criteria, dependencies, plans, implementation notes, findings, review notes or final summaries. Ask the owner for missing content. Implementation and backlog refinement do not authorize agents to add their own prose. Create tasks or drafts only when explicitly requested, using the owner's supplied content. Agents may check off existing items after verifying them and update workflow status as authorized below. Report evidence, bugs and suggestions in chat or PRs, without adding them to tasks. This rule overrides conflicting README, skill and Backlog.md CLI guidance. Small, mechanical changes may be completed without creating a task.
- `backlog/tasks/` is the single backlog. Use the Backlog.md CLI (`backlog task list`, `backlog task view`, `backlog task create`, `backlog task edit`) for task changes; the files remain ordinary Markdown in Git. Read `backlog instructions overview` for its CLI workflow. Install the CLI separately with `brew install backlog-md` if needed. Do not add it to the Swift package or use its optional web/MCP integration.
- The columns are `To Do` (unselected work), `Next` (owner-selected work agents may pick up), `Verify` (implementation finished, awaiting owner review), and `Complete` (owner-verified and ready for release). At the start of project work, list `Next` tasks and read the chosen task. Do not pull work from `To Do` on your own; a direct user request may move its task to `Next` first.
- Make each task self-contained and readable in the Backlog app. Explain the problem, why it matters, what should change, and how completion will be checked in complete sentences. Include essential context, scope, current findings and review limits in the task itself; do not link to repository files or put file paths in reference/documentation fields, because those files are not visible in the app. Use as much space as clarity requires, without a fixed word limit. Condense outdated session notes without removing the explanation, dependencies, status or checked criteria.
- Keep a task in `Next` while implementing. After relevant checks, check off supported existing acceptance criteria and move it to `Verify`, without adding agent-authored plans, notes or summaries. Leave `Complete` for the owner's verification or an explicit user instruction. If the owner requests changes, return the task to `Next`; any review-note content must come from the owner. Keep authorized backlog changes with the related code and changelog in the same commit.
- When the owner requests a new backlog item, use a draft for an idea that is not yet agreed work and a `To Do` task for agreed work. Include only content supplied by the owner; ask for missing input. Explain the supplied content without linking to other files. Keep the active task focused; report newly discovered work without silently expanding scope or adding backlog items.

## Development

- Use Conventional Commits for every new commit: `type(scope): description`, with an optional scope. Use `feat` for features, `fix` for fixes, `perf` for performance improvements, and `!` or a `BREAKING CHANGE:` footer for breaking changes. Documentation, tests, CI, refactors, and maintenance use their matching types. Do not rewrite older history to retrofit the convention.
- Think through assumptions before changing code. Prefer the smallest change that solves the request; avoid unrelated refactors.
- Keep the CLI usable without Xcode. Use Swift and command-line tools for builds and tests.
- Test code changes with the affected CLI command and a repository fixture. Reproduce pipeline issues in the CLI before debugging through the UI.
- After dependency upgrades, new features, or significant refactors, run `make build`, `make tests`, and `make evals-pipeline` on a fixture. Evaluation suites are the quality gate; run them sequentially. For a quick LLM smoke check, run `make evals STAGE=filename`.
- Never run multiple inference tasks in parallel. WhisperKit and llama.cpp share limited on-device GPU memory. Load Qwen once per pipeline run and reuse it across stages.

## Privacy

- Never read, copy, or use personal recordings or data from `processed/`, Obsidian, or CaptainsLog data folders for tests, evaluations, reproductions, or debugging.
- Use only repository fixtures under `eval/`, including `eval/transcribe/audio/` for audio tests. Treat evaluation inputs as synthetic fixtures; do not replace them with personal recordings.
- Set `CAPTAINS_LOG_CONFIG_PATH` to an isolated temporary config and data directory for CLI/app checks. Bypass default demo seeding; `demo/` and hard-coded design examples are presentation material, not evaluation inputs.

## Evaluations

Stage-specific evaluation workflows live in `skills/<stage>-eval/SKILL.md` for transcription, cleanup, filename, and enrichment. Use the relevant workflow when evaluating output. Reports should describe concrete changes and semantic impact, including missing or added content and hallucinations; scores alone are not enough. Human review makes the final quality judgment.

## Documentation

- Minimize PR review effort and text. State the change, give one quick review action or tip, and summarize checks and material limits. Keep detailed evidence in optional expandable PR sections, not agent-authored task notes. Proactively include a short video for UI changes, or a concise example, screenshot or sample output suited to other changes. Use synthetic fixtures and isolated data for media. Never imply an unperformed check or recording. Help the owner assess behavior without reconstructing it from code or logs.
- Update `CHANGELOG.md` in the same commit as every change, including code, prompts, dependencies, fixtures, tests, documentation, and tooling. Describe concrete changes under `Unreleased`; keep planned work in the backlog. Review `git status`, `git diff`, and `git log` so nothing is missed. Backfill using release tags as boundaries; do not invent earlier history.
- Prepare releases with `make release BUMP=auto|patch|minor|major|version` (preview with `ARGS=--dry-run`, push with `ARGS=--publish`). By default it infers the highest bump from commits after the latest reachable release tag: fix/perf → patch, feat → minor, breaking → major (minor for 0.x); maintenance-only commits do not trigger a release. Manual overrides remain available. It updates `VERSION`, dates and moves Unreleased entries, updates Git comparison links, runs sequential release checks, and creates a commit and tag. Record archive/cask publication in each release; generated cask-only version/checksum commits are covered by that entry. Follow the release checklist in `README.md` and review evaluation semantics before publishing.
- ALL ADR content must come from the owner, including decisions, context, rationale, alternatives and consequences. Agents may edit or rewrite supplied wording but must never originate ADR content. Create an ADR only when the owner explicitly requests it and supplies its content; ask for anything missing. Read relevant ADRs before architectural changes. For an authorized ADR, use `adrs` and keep it within 300 words (up to 500 for essential owner-supplied rationale). Editorial shortening must preserve the decision, date and status. Do not independently create a superseding ADR. This rule overrides conflicting architecture-documentation guidance.
- Keep `docs/` exclusively for numbered ADRs, with no plans, reports, guides or subfolders. Use the CLI for authorized owner-supplied task content, status changes and checking existing items. Keep synthetic reference data under `eval/` or `demo/`, separate from active suites when unused.
- Keep current commands and isolation rules in README and the existing script/skill instructions. Report evaluation evidence, native UI limits and legacy-code review in chat or PRs; do not add them to tasks or ADRs yourself. Keep ADR-007 focused on its owner-supplied test-runner decision. Check downstream SwiftPM clients, previews, debug flags and resource dependencies before deleting apparently unused public symbols or vendored headers.
